# Restic Monitor client protocol v1

The client protocol is intentionally small. Job configuration stays in the web UI; clients send only a run identifier, the command exit code, and optional selected Restic summary data.

## Provisioning

1. In the Access-protected UI, register the Host and Repository, then create one Job for each independently scheduled command.
2. Copy the Job's one-time `ping_url` into a protected setting on the machine that runs Restic.
3. If the URL is exposed, rotate it in the UI. Rotation revokes the old URL immediately.

The URL token is authentication. The UUID in the run path is not a secret: it correlates one command's start and completion and makes retries idempotent.

## Routes

The UI displays a URL with this form:

```text
https://ingest.example.com/api/v1/ping/{ping_token}
```

For each command, the client creates one UUID `run_id` and sends:

```text
POST {ping_url}/runs/{run_id}/start
POST {ping_url}/runs/{run_id}/complete
```

The start request has no body. The completion request uses `Content-Type: application/json` and requires `exit_code` from 0 through 255. Example:

```sh
RUN_ID="$(uuidgen)"
PING_URL='https://ingest.example.com/api/v1/ping/rmp1_REPLACE_WITH_JOB_TOKEN'

curl --fail --silent --show-error --retry 3 --retry-max-time 20 \
  --request POST "$PING_URL/runs/$RUN_ID/start" || echo 'start ping failed; continuing Restic' >&2

set +e
restic backup --json /data > backup.jsonl
RESTIC_EXIT_CODE=$?
set -e

# Parse backup.jsonl to add selected summary metrics if wanted.
printf '{"exit_code":%d}\n' "$RESTIC_EXIT_CODE" > completion.json
curl --fail --silent --show-error --retry 3 --retry-max-time 20 \
  --request POST --header 'Content-Type: application/json' \
  --data-binary @completion.json "$PING_URL/runs/$RUN_ID/complete" || \
  echo 'completion ping failed; check the Restic Monitor dashboard' >&2
exit "$RESTIC_EXIT_CODE"
```

The command above shows the route and minimum payload without parsing JSON output. Ready-to-adapt examples that parse synthetic Restic output are in [`examples/restic-monitor-bash.sh`](../examples/restic-monitor-bash.sh) and [`examples/restic-monitor-powershell.ps1`](../examples/restic-monitor-powershell.ps1).

Both sample clients capture Restic output and replay it after the process exits so they can parse the same output. Progress is therefore not streamed live by these examples. Adapt output handling to the existing scheduler or service if it needs live progress.

## Completion body

Only `exit_code` is required. Optional fields:

| Field | Purpose |
|---|---|
| `restic_version` | Version printed by `restic version` |
| `metrics` | Backup summary counters and optional snapshot ID; accepted for `backup` Jobs |
| `repository_stats` | `stats --json` measurement with explicit `restore-size` or `raw-data` mode; accepted for `stats` Jobs on exit code 0 |
| `error_summary` | Short sanitized diagnostic text; do not send raw logs or paths |

Unknown fields are rejected. Counters must be non-negative integers no larger than JavaScript's safe integer maximum. The body may not exceed 65,536 bytes. The server does not accept stdout, stderr, source paths, repository URLs, credentials, Job name, slug, operation, repository key, client timestamps, or client duration.

Backup JSON Lines map the final `summary` fields `total_bytes_processed`, `data_added`, `data_added_packed`, file counts, and `snapshot_id` into `metrics`. `stats --json` has one object; `total_size` must be paired with the mode selected by the client. `prune` has no JSON output and `forget --prune` can mix text and JSON, so report the exit code without parsing its output.

## Identity, timestamps, retries

- `ping_token`: per-Job capability used to authenticate. It is generated by the server, stored as a hash, and shown only at creation or rotation.
- `run_id`: client-generated UUID for one process invocation. Use a new one for every invocation and the same one for both phases and all retries.
- `event_id`, `workflow_id`, `event_type`, `job_key`, `repository_key`, and `schema_version`: not part of this v1 client contract.

The server records request receive time. It calculates duration only when it received a start ping; when completion arrives without a start, the result is stored with “start ping missing” and no duration. A late start cannot change a completed run back to running.

Retry the same URL and exact completion body. An identical completion is accepted as a duplicate; a different result for an already completed run returns `409 Conflict`. `401` means the URL is invalid or revoked; `409` needs operator review; `429` and `5xx` can be retried with bounded backoff. Keep the backup running if a ping fails: ping delivery must not replace Restic's own exit status. The sample clients make bounded delivery attempts, have no durable local queue, and return Restic's exit code.

## Exit status

The server treats exit code 0 as success, code 3 as partial success for the Restic operations that use it, code 130 as cancelled, and other non-zero codes as failed. Optional metrics do not change that status. A server-side alert is created for failed, partial, cancelled, missed-start, and timed-out results according to the Job's notification preference.

See the [OpenAPI contract](../packages/protocol/openapi.yaml) and the [Restic scripting documentation](https://restic.readthedocs.io/en/stable/075_scripting.html) for exact schema and Restic JSON details.
