# Restic Monitor implementation plan

- Status: redesign approved; implementation in progress
- API path version: v1 (no release or deployed client requires a protocol migration)
- Database baseline: resettable development database; no existing-data backfill or compatibility migration is required
- Scope: server-side Job configuration, ping API, schedule monitoring, Discord alerts, dashboard, and small Bash/PowerShell examples
- Out of scope: a required Reporter product, modifying an existing Docker/cron host, or editing the sibling `docker-restic` repository

## Product model

The server owns the configuration for a monitored Job. A Job has a name, description, slug, tags, operation, repository associations, schedule rules, grace/timeout policy, and notification preferences. A Job is one independently scheduled command with one result and alert history. Backup and prune therefore use separate Jobs; tags can group related Jobs. Several cron rules may belong to one Job when they invoke the same operation and have the same reporting meaning.

Hosts and repositories remain server-side inventory. `job_key` is removed from the client contract and the Job table. A mutable, human-readable `slug` identifies a Job in the UI and filters. It does not authenticate ping requests.

The UI creates a Job and generates a per-Job ping URL using a random capability token. The token is returned only when created or rotated, and only its SHA-256 hash and a short prefix are stored. The internal Job UUID and the ping capability are separate. Ping routes accept POST only; application logs must not record the full request path.

## Ping contract v1

```text
POST /api/v1/ping/{ping_token}/runs/{run_id}/start
POST /api/v1/ping/{ping_token}/runs/{run_id}/complete
```

`run_id` is one UUID generated by the client per invocation and reused in both paths and every retry. Start has no request body. The endpoint path supplies the Job and event phase, so the body needs no `schema_version`, `event_id`, `workflow_id`, `event_type`, `job_key`, `repository_key`, `operation`, client timestamps, or duration.

Completion requires `application/json` and an `exit_code` from 0 to 255. Optional fields are `restic_version`, a small set of allow-listed Restic summary metrics, Repository stats for `stats` Jobs, and a short sanitized `error_summary`. The API gets operation, host, and repository associations from Job configuration. Raw stdout/stderr, paths, repository URLs, and credentials are never accepted as stored output.

The Worker timestamps requests when received and calculates run duration. Repeating start with the same Job/run ID returns the original run without resetting its start time. Repeating completion with the same semantic JSON result returns the accepted result; a different result for a completed run is `409 Conflict`. Start and completion updates are atomic with metrics and alert state. A completion received before its start ping is still recorded with a zero/unknown duration marker; a later start cannot move a completed run back to running.

The client reports the Restic exit code. The server maps it using the configured operation: zero is success; the documented partial-success code is applied only to operations where Restic defines it; cancellation and all other non-zero codes are failures. Metrics are optional and do not affect run status. Delivery retries reuse the same run URL and body. The examples show bounded curl/PowerShell retries; a durable local spool is optional client behavior, not a server protocol requirement.

## Job, schedule, and notification configuration

Initial schedule support is standard five-field cron with an IANA timezone. The schema stores a schedule type and expression so interval and systemd OnCalendar support can be added separately. Several cron rules may be assigned to one Job; each rule has its own timezone and start grace. The Worker Cron remains one five-minute UTC trigger and evaluates a bounded number of rules per invocation.

Start grace is the wait after a scheduled occurrence for a start ping. Maximum runtime is separate and starts when the server receives the start ping. This prevents a short late-start allowance from incorrectly timing out a long Restic run. Both values are configured on the server.

Job registration includes Discord enablement. The Discord webhook remains a Cloudflare Secret shared by configured Jobs; per-job preferences determine which alerts enter the notification outbox. Existing exit-code reporting, schedule-missed/timeout detection, repository-stats growth alerts, deduplication, and notification retry behavior are retained.

## Fresh D1 data model

The local D1 can be deleted and recreated during this pre-release redesign. Keep one current initial schema for a clean setup; do not spend work preserving the old development data or old event protocol. The baseline schema includes:

| Table | Purpose |
|---|---|
| `hosts`, `repositories` | Admin-managed inventory |
| `jobs` | Name, description, slug, operation, host, timeout, enabled and Discord preference |
| `job_tags` | Job labels |
| `job_repositories` | Configured repository roles for a Job |
| `job_ping_tokens` | Hash-only, revocable per-Job ping capabilities |
| `job_schedule_rules`, `job_schedule_state`, `schedule_occurrences` | Typed schedule definitions and missed-run tracking |
| `runs`, `run_repositories`, `run_metrics` | Server-timestamped execution history and optional measurements |
| `repository_stats` | Job/repository-specific Restic measurements and anomaly state |
| `alerts`, `notification_deliveries` | Deduplicated alerts and durable Discord outbox |

## Implementation stages and acceptance tests

### Stage 1 — Contract and fresh schema

Replace the event envelope schema with the v1 start/completion route contract, OpenAPI, curl examples, and synthetic payload fixtures. Create a consolidated clean D1 schema reflecting Jobs, schedule rules, ping capabilities, runs, alerts, and Discord preferences. Remove old event-id/token tables and reset only this project's local Wrangler D1 state.

**Tests:** contract validation for valid/invalid completion bodies, missing/invalid IDs, unknown metrics, unsafe integers, and body size; D1 constraint tests for unique slugs, token hashes, Job associations, schedule rules, and run completion state.

### Stage 2 — Admin configuration API

Add Access-host-protected CRUD for Hosts, Repositories, Jobs, tags, repository associations, cron rules, Discord preference, and ping-token rotation. Generate a ping URL only on Job creation/token rotation. Validate cron/timezone/operation/server references before saving.

**Tests:** create/update/disable Job, duplicate slug, invalid association, schedule and timezone errors, one-time token return/hash-only storage/rotation, and rejection from a non-admin hostname.

### Stage 3 — Ping and run API

Implement POST-only start/completion endpoints. Resolve the ping token to one enabled Job, snapshot its operation/repository configuration on start, record server receive times, apply exit-code status mapping, store optional metrics, and make retries idempotent per Job/run ID.

**Tests:** start/complete success, partial and failed exit codes, repeated start without time reset, repeated identical completion, conflicting completion, concurrent run IDs, completion-before-start, revoked/unknown token, disabled Job, invalid body, and no credential or raw-output persistence.

### Stage 4 — Schedule engine and alert routing

Adapt missed-start and runtime-timeout processing to multiple cron rules. Apply each rule's timezone and start grace, retain catch-up/DST behavior, and only queue Discord notifications for Jobs that enable Discord. Keep the existing repository growth anomaly rule.

**Tests:** grace boundaries, two cron rules on one Job, same-time occurrence dedupe, DST transitions, Worker catch-up, missing start, timeout, late completion recovery, disabled Discord delivery, webhook retry and recovery notices.

### Stage 5 — Management and status UI

Add Host/Repository/Job registration and editing, schedule/tag/association/notification controls, one-time ping URL display and rotation, and Job status/history views. Keep the run and repository measurements dashboard.

**Tests:** static JavaScript checks plus UI/API flows for create, edit, invalid form values, hidden/one-time secret display, and post-creation ping examples using synthetic data.

### Stage 6 — Client examples and scope cleanup

Provide Bash/curl and PowerShell examples that run an existing Restic command, keep its exit code, optionally parse summary data, and send start/completion pings. Do not require a wrapper CLI, Docker image, spool, or quarantine. Classify current Reporter/shim/e2e work as optional legacy examples or remove it from default product checks after the new examples pass.

**Tests:** parser fixtures for Restic 0.19.1 backup JSON Lines and stats JSON, exit codes 0/3/130/unknown, malformed/partial output, HTTP retries, and stable run ID/body. These tests use fake Restic output and never initialize or access a real repository.

## Restic JSON handling for examples

The API stores only a small, stable subset parsed on the client. Restic `backup --json` emits newline-delimited JSON; the last successful `summary` contains `data_added`, `data_added_packed`, `total_bytes_processed`, file counts, and an optional `snapshot_id`. `stats --json` emits one JSON object, whose `total_size` depends on the selected mode. The client must send an explicit `mode` with Repository stats. `prune` does not currently support JSON, and `forget --prune` can mix JSON and text, so the examples report its exit code without trying to parse detailed prune output.

Restic exit errors can appear as a JSON `exit_error` on stderr, but runtime/argument failures may not follow that format. Use the process exit code as the required result and treat error text as optional, sanitized context. Numeric values above JavaScript's safe integer range are omitted instead of rounded. Restic documents that new output fields/message types may be added; parsers ignore unknown fields. See the [Restic scripting and JSON documentation](https://restic.readthedocs.io/en/stable/075_scripting.html).

## Deployment boundary

Local Vitest/Wrangler D1 tests do not deploy anything. Production setup remains opt-in: create a new D1 database from the clean schema, configure the Worker and dashboard Access policy, set the Discord webhook Secret, create Jobs in the UI, and install the generated ping URL in an existing scheduler. Never edit the sibling `docker-restic` repository as part of this project.
